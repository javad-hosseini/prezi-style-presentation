05 / 20STORAGE ARCH

ClickHouse چگونه داده را ذخیره می‌کند؟

هر INSERT یک Part کوچک می‌سازد؛ Partها ادغام و Partهای ادغام‌شده دوباره ادغام می‌شوند
↓ merge ↓
↓ merge ↓
برخلاف دیتابیس‌های سنتی، ClickHouse دائماً Rewrite نمی‌کند؛ Part جدید می‌سازد و در پس‌زمینه، Partهای کوچک را به Partهای بزرگ‌تر ادغام می‌کند.
06 / 20MERGETREE ENGINE

قلب ذخیره‌سازی ClickHouse

CREATE TABLE network_events
ENGINE = MergeTree()
PARTITION BY toYYYYMM(event_time)
ORDER BY (event_time, user_id)
مدیریت Data Partsمرتب‌سازیPartitionMerge خودکار

MergeTree مسئول مرتب‌سازی داده، Partition بندی و بهینه‌سازی Query هاست. انتخاب ORDER BY تاثیر مستقیم روی Performance دارد.

07 / 20BATCH INSERT

چرا Batch Insert برای MergeTree ضروری است

Batch Insert یکی از مهم‌ترین بهینه‌سازی‌های Performance برای موتور MergeTree است. چون هر Insert معمولاً یک Data Part جدید می‌سازد، تعداد زیاد Insertهای کوچک، تعداد زیادی Part کوچک تولید می‌کند.

هزاران Insert کوچک
1,000,000 INSERT
↓
1,000,000 Data Part
↓
فشار سنگین روی Merge
یک Batch Insert
۱ Batch INSERT
↓
فقط ۱ Data Part
↓
Merge سبک و سریع
کاهش تعداد PartCompression بهترOverhead کمتر StorageQuery سریع‌تر

به همین دلیل مستندات رسمی ClickHouse توصیه می‌کند به‌جای ارسال بسیاری Insert کوچک، داده را در Batchهای بزرگ ارسال کنیم.

09 / 20INTERNAL STORAGE

یک Query چطور فقط بخش لازم را از دیسک می‌خواند؟

۱. Primary Index
primary.idx
می‌گوید: ۵۰۰ در Granule ۲۰ است
۲. Mark File
age.mrk2 · name.mrk2
می‌گوید: Granule ۲۰ از کجای فایل شروع می‌شود
۳. Column File
age.bin · name.bin
فقط همان بخش خوانده می‌شود
تصویر ذهنی نهایی 🧠
Table
 └── Data Part
    ├── primary.idx
    ├── id.bin, name.bin, age.bin
    └── id.mrk2, name.mrk2, age.mrk2
زنجیره کامل
INSERT → Data Part → Granules
→ Primary Index → Mark Files
→ Column Files → Physical I/O
10 / 20QUERY OPTIMIZATION

چگونه Query ها سریع‌تر اجرا می‌شوند؟

Pruning یعنی «هرَس کردن» — ClickHouse قبل از خواندن، Partitionهایی که مطمئن است داده مورد نیاز Query در آن‌ها نیست را کلاً کنار می‌گذارد و اصلاً باز نمی‌کند.

روی یک ماه کلیک کنید — فقط همان یک ماه انتخاب و Scan می‌شود:
بدون Partition Pruning
۱۲ ماه Scan = 12.4B rows (کل جدول)
با Pruning
یک ماه را انتخاب کنید
ORDER BY(event_time,user_id) → Data Ordering + Partition Pruning
PARTITION BY toYYYYMM(event_time)هر Partition = یک ماه۱۲.۴B rows / ۱۲ ماه ≈ ۱.۰۳B rows در هر ماه
